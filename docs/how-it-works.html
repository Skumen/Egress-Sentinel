Egress Sentinel · exit node monitoring

How Egress Sentinel watches the exit nodes

Egress Sentinel checks every exit node once a minute from the monitoring server. An external sensor checks the same nodes from the users’ side of the network, and the results go to approved users as formal notices in Telegram. Most of the design is about one thing: an outage is announced only when it is real.

Architecture

Three vantage points

The monitor checks that each exit node answers. The sensor checks that traffic actually passes through it. Telegram is how people hear about it and act on it.

CDN distributes client configurations and carries no user traffic, so traffic verification is switched off for it in the dashboard. It is still checked directly.

Every 60 seconds

One check cycle

The order matters: a failed check only counts after the monitor has confirmed that its own network is fine.

  1. Advance the schedule

    Send due maintenance reminders, open windows that have started, close windows that have ended.

  2. Review the sensors

    A sensor that has been silent for three intervals is marked offline and its data is set aside.

  3. Check every node at once

    TCP connect, ICMP ping or HTTP GET, run in parallel, each with a 5 s timeout.

  4. Guard against itself

    If anything failed, probe the canary hosts. If they fail too, the monitor is offline: skip the cycle, alert no one.

  5. Merge sensor results

    Node answers, but a fresh sensor report says traffic does not pass: count it as a failed check, once per report.

  6. Apply transitions

    Move counters and statuses, open or close incidents in the log, and track latency streaks.

  7. Notify

    Queue the notices in order, filter muted categories, deliver to subscribers or administrators only.

  8. Persist

    Write node state after every cycle and history every 5 minutes, so a restart loses nothing.

False-alarm protection

Why an alert can be trusted

Every rule below exists to keep one failure somewhere else from looking like an exit node outage.

Threshold

Three strikes

A single lost packet or slow handshake never reaches users. An outage needs three consecutive failed checks.

Canaries

The monitor checks itself

When checks fail, well-known hosts are probed. If they fail too, the cycle is skipped and no alert is raised.

Sensor health

A broken sensor is set aside

The sensor verifies its own Russian and foreign connectivity and its Xray process. If either fails, it reports itself impaired and its results are ignored.

Once per report

One observation, one strike

A sensor report stays valid for a few minutes, but each report is counted only once.

Consensus

All sensors must agree

With several sensors, traffic counts as failed only when it fails for every one of them.

Hold

No false recoveries

An outage found by the sensor is cleared only by a new sensor result. A silent sensor does not count as the node coming back.

Hysteresis

Latency needs a streak

Three slow checks to declare, three normal checks to clear.

Persistence

Restarts are invisible

Counters, open incidents and acknowledgements are saved every cycle. After a restart the same incident continues with no repeated alert.

Access

Getting on the list

There is no shared group. Every recipient is approved individually and receives notices in a private chat with the bot.

  1. Request

    The user opens the bot, presses Start, then Request access.

  2. Review

    Administrators get the request with Approve and Deny buttons.

  3. Subscribe

    Approval subscribes the user to alerts and opens a read-only dashboard. Node addresses are never shown to users.

  4. Manage

    Users can switch notifications off themselves. Administrators can revoke access or send a notice.

Records

What is kept

state

Live state of every node and open incidents. Written every cycle.

history

5-minute buckets for 48 hours, hourly buckets for 90 days. Feeds the charts and 30-day availability.

incidents

The last 1000 outages and latency incidents, with start, end, cause and acknowledgement.

store

Nodes, schedules, users, notification texts and toggles, sensor registrations (token hashes only).

Timings and thresholds are the production settings. Examples in the scenarios are illustrative. VLESS links and keys stay on the sensor server; the monitor receives only “passing / not passing”, latency and exit IP.
