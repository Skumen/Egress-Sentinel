# Egress Sentinel

[English version](README.md)

Egress Sentinel следит за выходными узлами VPN- или прокси-сервиса (например, VLESS-серверами) и сообщает пользователям в Telegram, когда узел падает, начинает тормозить или перестаёт пропускать трафик. Уведомления строгие и по делу. Пользователей одобряет администратор, и они получают уведомления в личном чате с ботом, общая группа не нужна. Всё управляется из панели — мини-приложения Telegram.

```
🔴 INCIDENT NOTIFICATION — EXIT NODE OUTAGE
Status         OPEN
Severity       SEV-3 / MINOR
Issued         2026-10-14 12:03:00 UTC+3
Issued by      monitor-01
Administrator  Administrator
The monitoring system has detected a loss of availability affecting 1 of 4 monitored exit nodes.
Traffic routed through the affected exit nodes may be interrupted.

AFFECTED EXIT NODES
1. DE-1
Incident ID    INC-20261014-1201-5B4D
Direct check   Passing — the exit node responds
Traffic check  NOT PASSING · sensor MSK-1
Error          VLESS traffic not passing (sensor MSK-1): Tunnel could not be established
...
REQUIRED ACTIONS
1. If your connection is interrupted, switch to an available exit node listed above.
```

Зависимостей npm нет: мониторингу нужен только **Node.js 20.12+**. Необязательному сенсору трафика дополнительно нужны Xray-core и curl.

**Наглядно, как всё устроено:** откройте [docs/how-it-works.html](docs/how-it-works.html) в браузере. Там архитектура, цикл проверки, пошаговые сценарии инцидентов и защита от ложных тревог (на английском).

Уведомления бота и панель — на английском. Документация — на английском и русском.

## Возможности

**Мониторинг**
- Проверяет каждый выходной узел раз в минуту: TCP-подключение, ICMP ping или HTTP(S) GET.
- Недоступность объявляется после 3 неудачных проверок подряд (настраивается), а не из-за единичного сбоя.
- **Тревога по задержке**: три медленные проверки подряд — `PERFORMANCE DEGRADATION`, три нормальные — отбой. Порог можно задать для каждого узла.
- **Внешние сенсоры трафика (VLESS)**: небольшая программа на другом сервере, лучше в регионе пользователей, подключается к каждому узлу как клиент и подтверждает, что трафик действительно проходит. Узел, который отвечает, но не пропускает трафик, считается упавшим. См. [docs/SENSOR.ru.md](docs/SENSOR.ru.md).
- **Защита от ложных тревог**: прежде чем винить узел, мониторинг проверяет свою связь; неисправный сенсор отбрасывается, а не порождает сбои; каждый отчёт сенсора засчитывается один раз; при нескольких сенсорах нужно согласие всех.
- **Перезапуск ничего не теряет**: открытые инциденты, подтверждения и счётчики сохраняются каждый цикл и продолжаются с тем же ID.

**Для пользователей**
- Уведомления о падении, восстановлении, задержке и плановых работах в личный чат, в строгом корпоративном стиле.
- Отчёт `/status` с кнопками Refresh и Open dashboard.
- Панель: общее состояние, узлы, предстоящие работы, **история и графики** по каждому узлу (задержка и доступность за 24 часа, 7 и 30 дней), **журнал инцидентов**. Адреса узлов пользователям не показываются.
- Пользователь может сам отключить уведомления.

**Для администратора**
- **Доступ по одобрению**: пользователь нажимает Start → Request access, а вы получаете кнопки Approve / Deny.
- Добавление, изменение, удаление и сортировка узлов в панели; проверка перед сохранением.
- **Acknowledge** (прекращает повторные уведомления) и **обслуживание** прямо из тревоги.
- **Запланированное обслуживание** с объявлением и напоминанием перед началом окна.
- **Настройки уведомлений**: любую категорию можно выключить. Выключенная категория не уходит никому, но мониторинг и журнал работают. Если выключить объявление о работах, напоминание всё равно придёт.
- **Сообщения пользователям**: официальное `NOTICE FROM THE ADMINISTRATOR` выбранным пользователям, с журналом доставки.
- **Шаблоны уведомлений**: правка текстов без правки кода, с предпросмотром.
- **Сенсоры трафика**: регистрация, выпуск токенов, последние результаты; выключение проверки трафика у узлов без пользовательского трафика.

## С чего начать

1. Создайте бота через [@BotFather](https://t.me/BotFather).
2. Разверните мониторинг на отдельном сервере: [docs/INSTALL.ru.md](docs/INSTALL.ru.md) (около 30 минут, Debian или Ubuntu, Caddy или nginx).
3. Необязательно: поставьте сенсор трафика: [docs/SENSOR.ru.md](docs/SENSOR.ru.md).

Попробовать локально без Telegram:

```bash
cp config.example.json config.json
DRY_RUN=1 node index.js
```

В режиме `DRY_RUN` сообщения печатаются в консоль, а не отправляются.

## Уведомления

| Уведомление | Когда |
|---|---|
| ℹ️ MONITORING SERVICE STARTED | Запуск бота (администраторам) |
| 🔴 INCIDENT NOTIFICATION — EXIT NODE OUTAGE | `failThreshold` неудачных проверок подряд (ID `INC-…`) |
| 🟠 INCIDENT UPDATE — OUTAGE ONGOING | Узел всё ещё лежит и инцидент не принят, раз в `remindEveryMinutes` |
| ☑️ INCIDENT ACKNOWLEDGED | Администратор нажал Acknowledge |
| 🟢 INCIDENT RESOLUTION — SERVICE RESTORED | Узел снова работает, с общим временем простоя |
| 🟡 PERFORMANCE DEGRADATION — HIGH LATENCY | Задержка выше порога `latencyChecks` проверок подряд (ID `LAT-…`) |
| 🟢 PERFORMANCE RESTORED | Задержка в норме `latencyChecks` проверок подряд |
| 📅 SCHEDULED MAINTENANCE NOTICE | Запланировано окно обслуживания (ID `MNT-…`) |
| 📅 UPCOMING MAINTENANCE REMINDER | За `maintenanceNoticeMinutes` до начала окна |
| 📅 SCHEDULED MAINTENANCE CANCELLED | Запланированное окно отменено |
| 🔧 MAINTENANCE WINDOW OPENED / EXTENDED / CLOSED | Начало, продление и конец обслуживания |
| 📨 NOTICE FROM THE ADMINISTRATOR | Администратор написал пользователям (ID `MSG-…`) |
| 📡 TRAFFIC SENSOR CONNECTED / IMPAIRED / OFFLINE / RESTORED | Состояние сенсора (администраторам) |
| 🛠 CONFIGURATION CHANGE NOTICE | Изменён узел или шаблон (администраторам) |
| 🔐 ACCESS REQUEST | Новая заявка на доступ с Approve / Deny (администраторам) |
| ✅ ACCESS GRANTED / ⛔ DECLINED / ⛔ REVOKED | Пользователю — решение по заявке |
| 📋 STATUS REPORT | Ответ на `/status` |

Уровень серьёзности считается по узлам не на обслуживании: **SEV-1 / CRITICAL** — недоступны все, **SEV-2 / MAJOR** — половина и больше, **SEV-3 / MINOR** — меньше половины.

Заголовки, вступления, блок REQUIRED ACTIONS и подпись можно править в **Administration → Notification templates**. Таблицы с данными формируются автоматически и сломаться не могут: текст администратора всегда показывается как обычный текст.

## Настройки

### `.env`

| Переменная | Что это |
|---|---|
| `TELEGRAM_TOKEN` | Токен бота от @BotFather |
| `ADMIN_IDS` | Telegram user ID администраторов через запятую. Обязательно: администраторы одобряют заявки |
| `CHAT_IDS` | Необязательно: группы, куда дублировать тревоги. Их участники получают доступ без заявки. Пусто — только личные сообщения |
| `WEBAPP_URL` | `https://ваш-домен` — адрес мини-приложения. Пусто — мини-приложение выключено |
| `WEBAPP_PORT` | Локальный порт веб-сервера, по умолчанию `8080` |
| `WEBAPP_SHORT_NAME` | Необязательно: короткое имя приложения из `/newapp` в @BotFather |
| `DRY_RUN` | `1` — печатать сообщения в консоль вместо отправки (только для отладки). Не запускайте параллельно с сервисом: оба пишут в одну папку `data/` |

### `config.json`

Создаётся из `config.example.json`. После правки `.env` или `config.json` перезапустите сервис.

| Параметр | Что значит | По умолчанию |
|---|---|---|
| `adminName` | Имя в строке *Administrator* | `Administrator` |
| `monitorName` | Имя сервера мониторинга в *Issued by* | имя хоста |
| `timezone` | Часовой пояс для времени в сообщениях | `UTC` |
| `intervalSeconds` | Как часто проверять | `60` |
| `timeoutSeconds` | Сколько ждать ответа | `5` |
| `failThreshold` | Сколько сбоев подряд нужно для тревоги | `3` |
| `remindEveryMinutes` | Интервал напоминаний, пока инцидент не принят (`0` — не напоминать) | `60` |
| `latencyThresholdMs` | Порог задержки для ping и TCP, мс (`0` — без тревог по задержке) | `300` |
| `latencyThresholdHttpMs` | Порог задержки для HTTP, мс (`0` — только если задан у узла) | `0` |
| `latencyChecks` | Сколько медленных проверок подряд нужно для тревоги (и нормальных — для отбоя) | `3` |
| `maintenanceNoticeMinutes` | За сколько минут до запланированного обслуживания напомнить (`0` — только объявление) | `60` |
| `notifyOnStart` | Сообщать администраторам о запуске бота | `true` |
| `servers` | Начальный список узлов, используется только при первом запуске. Обычно пустой: узлы добавляются в панели | `[]` |
| `canaries` | Адреса для проверки связи самого мониторинга | см. `config.example.json` |

HTTP-проверка считает успехом любой код ниже 400 и проходит редиректы. Для HTTP-узлов время включает DNS и TLS, поэтому тревога по задержке выключена, пока у узла не задан свой порог.

## Команды в чате

| Команда | Где | Что делает |
|---|---|---|
| `/status` | личка, группа | Отчёт о состоянии с Refresh и Open dashboard |
| `/subscribe` | личка | Получать тревоги в личные сообщения |
| `/unsubscribe` | личка | Отключить тревоги |
| `/myid` | везде | Ваш Telegram user ID (для `ADMIN_IDS`) |
| `/chatid` | везде | ID текущего чата (для `CHAT_IDS`) |
| `/help` | личка, группа | Список команд |

`/status`, `/subscribe` и панель доступны одобренным пользователям, администраторам и участникам групп из `CHAT_IDS`. Остальным на `/start` бот предлагает подать заявку. Acknowledge, Maintenance, Approve и Deny срабатывают только у администраторов.

## Данные

Всё хранится в папке `data/` рядом с `index.js`:

| Файл | Что хранит |
|---|---|
| `store.json` | Узлы, расписание обслуживания, пользователи и заявки, изменённые тексты, выключенные категории, сообщения администратора, сенсоры (только хеши токенов) |
| `state.json` | Текущее состояние узлов и открытые инциденты |
| `history.json` | История проверок: интервалы по 5 минут за 48 часов и по часу за 90 дней |
| `incidents.json` | Журнал инцидентов (последние 1000) |

Доступность считается по истории за 30 дней. Периоды, когда бот не работал, не было интернета или узел был на обслуживании, не учитываются.


## Ограничения

- Если упадёт сам сервер мониторинга, сообщить об этом будет некому. Подключите для него внешнюю проверку доступности (подойдёт любой бесплатный сервис мониторинга).
- Пока бот не работает, проверок нет: на графиках разрыв, в доступности этот период не учитывается. Если запланированное окно целиком прошло, пока бот был выключен, оно помечается как пропущенное, без сообщений о начале и конце.
- Задержка на графиках — средняя за интервал (5 минут, 1 час или 4 часа). Короткие всплески видны в пиковом значении.
- Самоподписанные HTTPS-сертификаты в HTTP-проверке считаются ошибкой. Для таких узлов используйте проверку TCP на порт 443.
- Сообщения администратора рассылаются по одному получателю; на сотню получателей уходит несколько секунд.

## Разработка

```bash
npm test
```

запускает юнит-тесты: проверку подписи Telegram, агрегацию истории, логику сенсоров и разбор ссылок VLESS. Кроме Node.js ничего не нужно.
